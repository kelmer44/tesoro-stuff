## 2. Animations (about 1,300 lines for the whole layer) ✅ done (slice f continues as callers arrive)

Files: `core/animimage.*`, `core/animbank.*` (337 lines in the `.cpp`, which holds both `AnimBank` and `AnimPlayer`), `core/animset.*`.

**Goal:** load one animation, show a picture from it, then make it play over time.

The four classes, and how they depend on each other:
- `AnimImage` is one picture, kept as the blob stored in the archive. It does **not** expand the spans: it only reads the blob and checks it
  (the offsets must fit inside it), and rewrites the items of shadow images. The spans (runs of pixels per row, stored as RGB565) are expanded only when the picture is drawn, in
  `RenderQueue::queueRows` and `Display::compose` (step 3).
- `AnimBank` is the data of one animation file: its steps (`AnimStep`: image, offset, movement, duration, hit rectangle; some have no image) and their images. It is shared.
- `AnimPlayer` is playback state over a bank: which step is current, when it started, loop and pause flags, and the movement the current
  step gives the object. The bank is held through a shared pointer, so copies of a player share the bank and keep their own state.
- `AnimSet` is the animations of one game object: one `AnimPlayer` per bank, of which one is current.

## 3. Screen (about 1,050 lines: `renderqueue.*` 644, `display.*` 168, `textqueue.*` 196) ✅ done

Files: `core/renderqueue.*`, `core/display.*`, `core/textqueue.*`.
Needs: step 2 (images and the player), and the clock for the check of 3e.

**Goal:** replace the throwaway `drawImage` by the real screen: objects hand images to the screen during the frame, then one `compose` turns them into pixels.

How it works, so the pieces make sense:
- The screen is **not** painted image by image. Each of the 480 rows keeps a list of horizontal **spans** (a start column, an end column, a depth, and where the pixels come from).
- Queuing an image adds its runs to the rows. A run with a smaller **depth** is nearer: it cuts the spans behind it, and what is behind it never needs drawing.
- `compose` then walks each row left to right and copies the pixels of each span into the frame. The spans of a row are laid down one after the other from the row's start, so **a row must be covered end to end**: the game always draws a full-screen background first (and the old code leaves an empty row untouched).
- Scaled images (the pointer, characters) are different: they are painted straight into the frame during `compose`, and only their visible pieces are entered in the row lists.
- The screen class is `Display` (`core/display.*`). Its three requests are named `queueImage`, `queueImageScaled` and `queueText`, because they only queue: nothing is drawn until `compose` (a plain `draw` is kept for an object's own `draw` method). On `codex/remove-hosts` it is one plain class: it used to be `Display` behind an abstract `Display` base with no other implementer, and the two were merged. Objects take a `Display &` in `draw`; forward-declare `class Display;` in object headers and include `display.h` only in the `.cpp` files that draw.

## 4. Level and objects (menu level first) ✅ done (4i waits for steps 5 and 10)

Files: `core/objectlist.h`, `core/object.*`, `core/camera.*`, `core/room.*`, `core/cameraframe.*`, `core/spriteobject.*`, `core/level.*` (473 lines in the `.cpp`), and `core/animset.*` from step 2.
Needs: steps 2 and 3.

**Goal:** load a level file and draw it with its camera. `PRINCIPAL.LVL`, the main menu, is the best first target: it has one camera frame, one background picture and two menu items.

The pieces:
- A **level** is itself an object. It holds the animation banks (one `AnimPlayer` each, the prototypes that objects copy), the rooms, and every object. A **room** keeps its objects ordered by x. Each object record says its position, name, which banks it uses, its kind, and kind-specific data bytes.
- `Level::createObject` is a factory that switches on the kind. Start it with only the kinds you have (0, 1 and 3) and let the others warn and be skipped; the finished code does the same, so a level loads even if you have not ported its other kinds.
- The **camera** has bounds and a position; each room scrolls with a divisor (parallax), and everything is drawn at `x - camera.scaledX + 0x140`, `camera.scaledY - y + 0xf0` (world Y points up, the screen centre is 320, 240).

**Goal:** Jim stands in a level at the right size, walks to where you click, and goes round obstacles.

How it works, so the slices make sense:
- Floors and walk areas are shapes stored as **points inside an animation step** (step type 4: each point has x, y and a scale, so Jim shrinks far away). `WalkFloor` (kind 7, named `SUELO`) gives the size at a point; `PathObject` (kind 8, named `PATH`, or `CAMINOS` in the tavern) gives the waypoints of the route round obstacles. The floor names its path object in its data; the level's kind 1 object (`CameraFrame`) names the floor.
- Jim is one object that lives in whichever level the player is in. He has nine animation banks (four speaking, four walking, one standing). When he stands he is not in the main list; his size is worked out once, when he enters a level or stops. While he walks he is put in the main list at priority 5, which runs before the pointer (`0xf`), and taken out when he arrives.
- A walk keeps his position in 24.8 fixed point (`x * 256`). Each frame the walk animation's own movement is scaled by his size (0x100 is life size) and kept on the straight line to the target. Facing is 1 up, 2 down, 3 left, 4 right, chosen by the longer distance.
- His walking banks have a single point for a hit shape (`makeSinglePoints`). When that point crosses the edge of the floor's outline, the collision pass calls `Jim::onTouched`, which swaps a straight walk for the route round the waypoints (6e).

**Goal:** the opening scene runs; a spoken line plays with its subtitle; a conversation shows its choices.

How it works, so the slices make sense:
- **A spoken line** is named by an ID such as `OBJ125T03`. The name key (`nameKey64`) is the first 12 characters at 5 bits each, so lookup ignores case and anything past the 12th character. The four text files are searched in a fixed order; a script keeps the result as one number (the table in the top byte, the line plus one below), `0` for no such line. The voice is the archive entry `ID.WAV`; a line with no voice has `wavOffset` 0 and stays on screen until the player skips it.
- **Sound** is a mixer with up to three voices at once, each with an id the speaker polls. Music is a track played through ScummVM's audio CD manager.
- **A speaker** (`Speaker`) is the part of an object that says a line: it pauses the object's animation, switches to a speaking pose, joins the main list at priority 6, and leaves when the voice has finished or the player skips. Jim is the only speaker until 9b (`Character`, kind 5), but the `SpeakingObject` interface stays because both implement it.
- **A script block** is a named list of 24-byte commands (say, sleep, jump, menu, send a message to an object, run another block, and so on) read from the four `.DLG` files. A running block is an object in the main list at priority 0x1e; each frame its turn returns 2 (still waiting) or 3 (did something).
- **What the scripts reach that is not ported yet:** characters (9b), the held item (9e), the board game (9g) and the movies (8h). In 8f those branches are left out with a warning, and each comes back with its own slice.
- **Order:** 8b to 8d need only 8a. 8e needs 8a. 8f needs 8d (a block makes Jim speak) and 8e. 8g needs 8f. 8h needs only the engine, and `Scripts::playVideo` links it up in 8f, so it can be done at any point after step 5.

## After the port is complete

- **Paint everything instead of queuing spans** (untried, optional): see `re/RENDER_SIMPLIFICATION.md`. It could remove `renderqueue.*` if a
  side-by-side comparison of recorded frames shows no difference.
- **Test the pointer at its end position instead of sweeping its move** (untried, optional, a deliberate deviation): the collision pass
  tests each moved object along its whole movement for the frame (`sweepRects`, a fraction of the move as the touch time, touches
  ordered by that fraction and then by depth). For the pointer this only matters when a fast mouse flick crosses a hotspot and stops
  beyond it: the label then shows for one frame. A click is only handled for an object that was also under the pointer the frame
  before, so a fly-by never clicks. Jim moves a few pixels a frame (not measured against the thinnest walk area). The simpler form
  is a plain overlap test of the rectangles at the end position, touches ordered by depth alone. It would remove the fraction, and
  with it the part of `shapedContactTime` (5f) that starts its pixel test at that fraction, so read what 5f does with it first.
  Check by recording the touch lists of a scripted play-through with both versions and comparing; list the one-frame labels
  as the known difference.
- **Put the object kinds in a folder of their own** (untried, optional, a layout change only): `core/` mixes the engine's machinery
  (archive, animation, display, camera, level, lists, collision) with the classes of the level file's object kinds (`CameraFrame`,
  `SpriteObject`, `MenuItem`, `Cursor`, `WalkFloor`, `PathObject`, `InteractiveObject`, `Character`, `StoryCharacter`, `ExitDoor`,
  `StoryProp`, `InventoryItem`, `InventoryStrip`, `ItemGroup`, `ClickCatcher`, `MapPlace`, `NoteObject`, `BoardColumn`,
  `MenuButton`, `SlotLabel`, `PathSprite`, `DepthZone`, `ShadowSprite`, and Jim). A folder such as `core/objects/` would hold them,
  and `Object` and `Level` (the base and the container) would stay in `core/`. Do it once all kinds are ported, in one commit that
  only moves files and changes include paths and `module.mk`, so the history stays readable and nothing else changes. Check it
  with a clean build and by loading a level of every kind. It does not change behaviour.
- **Reconsider `StdioText`** (untried, optional): it copies the original's `scanf`-style reading (stream position, `%i`, `%[set]`) so that
  `SpeechTable` and `ScriptBlock` parse like the original. Replace it only if a reviewer objects. Plain `sscanf` is allowed in
  engines (only `FILE`, `getc` and `fscanf` are banned) and could read the speech tables (`%[^,]`, `%[^"]`, with `%n` for the position).
  It is not safe for the script blocks: `%[0-\xa1]` is a range scanset, which the C standard leaves implementation-defined.
  `StringTokenizer` does not fit either, as the formats match single characters inside words. If you change it, compare the parsed
  tables and blocks with the current output on every shipped `*.TXT` and script file, and on damaged copies.

## Notes
- The branch has no accessors that only the comparison drivers used. Do not look for `AnimPlayer::startTime`, `totalDuration`, `loopX`, `loopY` or
  `pausedAt` (the player keeps those as private fields and reads them itself), nor `Jim::fixedX`/`usedMoveX`, `Cursor::companion` or
  `SoundDevice::lastId`/`activeCount`. Write only the accessors a caller needs.
- No class has a host interface any more. Objects hold a `World &` (or `World *`) and call it directly; scripts call `Scripts` (`scripts.h`).
  `SpeakingObject` is the one interface left, because both `Jim` and characters implement it.
- `core/wrap.h` holds `wrapMul`, `wrapAdd` and `wrapSub`: 32-bit arithmetic that wraps like the original's (a plain signed operation would be undefined behaviour on overflow). It replaces private copies the code used to have (`mulw` in the render queue and the set in the camera; collision no longer needs it since `sweepRects` was simplified). Copy it before the first file that needs it: step 3e or 4c, whichever comes first.
- Random numbers: use a `Common::RandomSource` in the engine (`randomBetween(min, max)`); there is no `core/random.*` to copy.
- Option "Enable cut content" (config key `cut_content`, on by default). It needs four pieces: the flag `GAMEOPTION_CUT_CONTENT` in `detection.h`, the
  game entry listing it in `detection_tables.h`, the entry in `metaengine.cpp`'s option list, and `World::cutContent()`. Only `PathSprite`'s wait test
  reads it (step 9): on, the wait is measured in seconds; off, it is the original's test, which never lets the three tavern walkers start.
  A game added to ScummVM before the flag existed must be re-added to show the option; the default is on.
- Match the original's behaviour first; the contracts mark open questions and port deviations.
- Do not add test hooks to the engine (`AGENTS.md`). Compare by running the game.
- Copy function by function, in the order above, and build after each.
