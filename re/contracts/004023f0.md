# 004023f0 — inferred_Cursor_SetText
Status: emu-compared · Cluster: 5 · Convention: thiscall(Cursor *this, const char *text, int colour) — RET 8

**Purpose (confirmed):** Sets the label shown next to the mouse pointer (the name of what is under it) and optionally its colour.
**Behaviour:** text null: only the first byte of the buffer at +0x78 is set to 0 (the rest of the old text stays). Otherwise the string including its terminator is copied there, without a length limit (the buffer is 0xa0 bytes, up to the colour at +0x118). Then, if colour > 0, its low 16 bits are stored at +0x118; 0 and negative values leave the colour alone.
**Callers:** 0040f050 Obj_ShowHoverText (the name of the object under the pointer, colour 0xffff, a 565 white), 0040f0b0 Obj_ClearHoverText (null, 0), and the null/-1 calls of 00407d00 Dialogue_ChoiceMenu, 0040dfc0, 00414c40 Exit_Activate, 00415350 and 004178b0. The cursor's draw (00402d80) draws the text with the colour at +0x118.
**Port:** HoverText::set (core/hovertext.h): the label as its own small class; the cursor will own one. **Validation:** Differential check `re/tools/run_startup_check.sh` (gen_vectors_hovertext.py + drivers/hovertext_driver.cpp): the original Cursor_SetText run in Unicorn on a zeroed fake cursor, 500 cases of 2-12 calls (texts of 0-100 characters with accented bytes, null text, colours -1, 0, 1, 0xffff, 70000, negative, 0x12345678), after each call compared the whole 160-byte buffer and the colour: 3989/3989. Mutations caught: clearing the whole buffer on a null text, accepting colour 0, clamping the colour instead of truncating it. Not covered: texts of 160 characters or more (the original copies over the fields after the buffer; the port truncates and warns).
**Open questions:** none.
