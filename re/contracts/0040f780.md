# 0040f780 — inferred_List_Remove
Status: emu-compared · Cluster: 27 · Convention: thiscall(List *this, value) — RET 4 · returns bool in AL

**Purpose (confirmed):** Removes the first element equal to value.
**Outputs / state written:** rewinds and walks (see List_PushBack); on the first element whose value equals the argument: cursor.next := node.next, node.next := free-list head, free-list head := node; returns 1. If nothing matches returns 0 (only AL is defined). The cursor is left where the search stopped (not rewound): after removing the first element the cursor is on the head with the at-start flag already cleared, so a following step would skip the new first element.
**Port:** CursorList::remove. **Validation:** Differential check `re/tools/run_startup_check.sh` (gen_vectors_list.py + drivers/list_driver.cpp): the original list code run in Unicorn on real list memory (pool allocator replaced by a zeroing bump allocator) with 600 random operation sequences of 2-40 operations (capacity 1-14, repeated and unique values, negative priorities), each followed by a full dump of the chain and the cursor's data slots, vs engine CursorList: List state 5876/5876, List remove result 1448/1448, ObjectList state 6865/6865, RemoveByObject result 1867/1867, EndFrame result 966/966. The port was first a linked list in an array, then rewritten as a plain array with a cursor index; both versions pass every comparison. Four of five deliberate mutations of the first version were caught (one by hanging), and all five of the array version. Not covered: the cursor's start flag after Clear (every operation rewinds first, so nothing here can see it), stepping after Remove without a rewind (no such function exists; only inlined copies in other classes), node pool exhaustion, lists sharing one pool (Ctor with a source list), FindByKey (predicate search; not run in the emulator), the ObjectList cursor position (the generator only probes the List cursor, with the insert-after-cursor function).
